# 4. Embedded ABIs in production; abigen v2 bindings only for test doubles

Date: 2026-10-22
Status: accepted

## Context

oraclewatch calls a handful of view functions on three kinds of contracts: the
`AggregatorV3Interface` of a proxy, the proxy's own `aggregator()`/`phaseId()`, and an
aggregator's `minAnswer()`/`maxAnswer()`/`typeAndVersion()`. Hand-written ABI encoding
is error prone, so the plan was to use typed bindings generated by `abigen`.

go-ethereum 1.17 marks the v1 `bind` package deprecated; v1 bindings also need
`eth_getCode`, which is outside the RPC methods oraclewatch allows itself. The v2
generator produces `PackX`/`UnpackX` functions plus a `BoundContract` for transactions.

The first implementation used v2 bindings. A test that lists the binary's dependencies
(`cmd/oraclewatch/imports_test.go`) then failed: `accounts/abi/bind/v2` imports
`accounts/keystore` and `accounts/external` (its `auth.go` builds transactors from a
keystore or an external signer). Nothing called that code, but it was linked into a
program whose security argument is that it contains no key management at all.

## Decision

- ABIs live in `internal/feeds/abi/` with their provenance in `SOURCES.md`: the official
  npm package for `AggregatorV3Interface`, and the Sourcify-verified ABI of deployed
  contracts for the proxy and aggregator subsets (the npm package does not ship them).
  Only view functions are kept.
- Production code embeds those files with `go:embed` and uses `accounts/abi` directly
  (`internal/feeds/abi.go`): one `pack` helper and small typed `unpack` helpers with
  checked type assertions. That is the part of a generated binding oraclewatch needs.
- Calls go through `chain.Caller`, whose only method is `CallContract` (`eth_call`).
- `abigen --v2` (pinned as a Go tool dependency in `go.mod`) is used for the Solidity test
  doubles, which do need transactions on the simulated chain. Their bindings and the
  deploy helper are compiled only with the `integration` build tag.
- The import test forbids `accounts/abi/bind`, `accounts/keystore`, `accounts/external`,
  `accounts/usbwallet`, `ethclient/simulated` and the test doubles in the binary.

## Alternatives

- **v2 bindings everywhere.** Typed and generated, but links key-management code into the
  binary. Rejected because of that dependency, and kept for tests.
- **v1 bindings.** Deprecated, require `eth_getCode`, and also link `bind`.
- **Copy the generated v2 code without its `bind` import.** Would be a hand-maintained
  fork of generated code; the embedded-ABI helpers are shorter and clearer.

## Consequences

- About 80 lines of hand-written decoding replace generated code; they are covered by
  unit tests, integration tests against the Solidity mocks, and a fuzz test on all
  decoders (a malicious RPC controls these bytes).
- The read-only property is enforced by the dependency graph and by a test, not only by
  convention.
- Changing an ABI is a reviewed diff of the JSON file and, if needed, of the typed helper.
